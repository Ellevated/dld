Общее: зелёная галочка выглядит одинаково, стоит ли она над настоящей ассерцией или над
проверкой, которая физически не имеет power. В нашей воронке это дороже, чем в человеческой:
`_pueue_add`-стаб и `check-tree-sync` прошли tester, pre-check, spec compliance и code quality —
все четыре гейта читают «критерий выполнен», ни один не спрашивает «а мог ли он не выполниться».

**Внешнее подтверждение.** Отрасль пришла к одному ответу — доказывать power критерия
**мутацией**, а не чтением:
- `spec-verify` (Claude Code skill, freeCodeCamp, 2026-08-26): на каждый Given/When/Then
  генерируется одна **прицельная** мутация; если тест переживает мутанта — вердикт `VACUOUS`,
  и он **fail-closed блокирует «done»**, поимённо. Отдельный вердикт `UNVALIDATABLE` для
  недетерминируемого — снимается только именной подписью человека с описанием метода проверки.
  Ключевая мысль ровно про нас: `VACUOUS` и `UNVALIDATABLE` — противоположности, а не градации;
  склеишь их — либо простишь пустые тесты, либо заблокируешься навсегда.
  <https://www.freecodecamp.org/news/how-to-stop-letting-ai-agents-fake-their-own-tests/>
- tianpan.co, «The Test the Agent Wrote That Tests Nothing» (2026-05-17): агент пишет тест **от
  кода**, а не от отказа, поэтому первый прогон зелёный по построению; практическое правило —
  мутация только по изменённой поверхности PR, red-green дисциплина («покажи тест красным до
  фикса») и ревью **ассерции**, а не дельты покрытия.
  <https://tianpan.co/blog/2026/05/17/test-agent-wrote-that-tests-nothing>
- Antigravity Lab (2026-06-30): три формы пустоты — over-mocking, тавтология, snapshot
  rubber-stamping; замер 91% line coverage при 47% mutation score. Дешёвый статический сигнал,
  применимый к нам без Stryker: **отношение числа моков к числу ассерций** в тесте.
  <https://antigravitylab.net/en/articles/app-dev/antigravity-ai-generated-tests-coverage-theater-mutation-score-audit-field-notes>

Заметим: наш собственный протокол RED-до-фикса это уже требует (BUG-218 писал регрессии
«RED 9/2 до фикса», TECH-221 — EC-1..EC-6), и там, где он соблюдён, дефект не проходит. Дыра не
в отсутствии правила, а в том, что оно применяется к **тестам** и не применяется к
**AV/EC-строкам приёмки**, чьё «средство проверки» — скрипт или команда, а не pytest.

**Proposed action** (Гермесу на рассмотрение, два независимых куска):
1. **Дешёвый и механический, сегодня:** в Spark Phase 5.5 / spec-compliance добавить проверку
   AV/EC-строк, чьё средство проверки — команда: запустить её на **немодифицированном**
   merge-base. Критерий, зелёный до начала работы, — `VACUOUS`, error. Это `wc`-класс проверки:
   True/False без модели.
2. **Точечно, отдельной спекой:** починить `test-wrapper.mjs` — ветка «`./test` существует, но
   это директория» должна возвращать `TEST_COMMAND_UNAVAILABLE` + exit 2, как absent-случай
   (CLAUDE.md уже обещает это поведение). Сейчас каждый прогон в этом репо получает
   `FAIL: 0 failure(s)` и его приходится опровергать из-за контекста.

## L2: разрушающие git-команды уходят в прод без анализа конкурентного писателя

**Frequency:** 4 occurrences. **Evidence:** diary `2026-08-30-TECH-221-task4-problem.md`;
SIGNAL-2026-08-30-1832; memory `lifecycle push-race divergence` (фикс rebase-recovery de4f434,
2026-06-21); `.claude/hooks/hooks.config.mjs:69` (проверено сегодня, см. ниже).
**Type:** failure_pattern

TECH-221 Task 4 отгрузил continuation-push как голый `git push --force-with-lease`. Голый lease
**удовлетворяется фоновым fetch'ем**, который обновил `refs/remotes/origin/<branch>`, ничего не
интегрировав. `orchestrator.py:106` прямо документирует, что gate-daemon фетчит эти репозитории
конкурентно — то есть это была живая гонка на этой машине, не теоретическая. Воспроизведено на
одноразовом репо: третья сторона пушит отревьюенный коммит, идёт фоновый fetch, идёт наш push →
**exit 0, человеческий коммит уничтожен**. С `--force-if-includes` — exit 1, отказ.

Дефект прошёл tester, pre-check, spec compliance и code quality review. Поймала его PHASE 3
Exa-верификация — **неблокирующий веб-поиск**. То есть единственное, что стояло между нами и
потерей чужой работы, — необязательный шаг.

**Внешнее подтверждение — это не наша находка, это документированное поведение git.**
`git-push(1)`, дословно: «supplying this option without an expected value, i.e. as
`--force-with-lease` … **interacts very badly** with anything that implicitly runs `git fetch` on
the remote to be pushed to in the background… this is **trivially defeated** if some background
process is updating refs in the background». И там же — точное лекарство: `--force-if-includes`
(git 2.30+) проверяет по **reflog**, что tip remote-tracking ref реально интегрирован локально.
<https://git-scm.com/docs/git-push> · подтверждение практикой:
<https://stackoverflow.com/questions/65837109/when-should-i-use-git-push-force-if-includes>
(«если ты фетчишь перед `--force-with-lease`, ты по сути форс-пушишь без всякой защиты»).

Иными словами: правило существовало в man-странице всё это время, а найдено было
воспроизведением гонки после отгрузки.

**Четвёртая копия правила ещё жива и уже устарела** — проверено сегодня:

```
.claude/hooks/hooks.config.mjs:69
  '  git push --force-with-lease  # checks remote state first\n'
```

Хук подсказывает голый lease как *безопасную* форму. TECH-221 починил 6 push-сайтов в двух
деревьях промптов, но подсказку хука — нет. Пересечение с K3 (`findings-2026-08-30.md`): правило
живёт копиями в прозе и расходится; это её **четвёртое** попадание за две сессии.

**Proposed action:**
1. Завести в `.claude/agents/review.md` категорию **git-safety** (сейчас категорий 0-6, ни одной
   про разрушающие операции): для любого диффа, содержащего `push --force*`, `rebase`,
   `reset --hard`, `branch -D`, `worktree remove --force` — обязательный вопрос «кто ещё пишет в
   этот ref, и что происходит, если он написал между нашим fetch и нашим push?». Категория с
   severity, а не совет.
2. Поправить `hooks.config.mjs:69` на `--force-with-lease --force-if-includes` — иначе хук
   продолжит учить агентов той самой форме, которую мы только что признали дырой.

## L3: продовые модули паркуются ровно на потолке LOC, и это уже норма, а не исключение

**Frequency:** 5 occurrences. **Evidence:** diary `2026-08-30-TECH-221-advisory.md`
(`orchestrator_queue.py` 400/400); `findings-2026-08-30.md` §«ниже порога»
(`gate-daemon.py` 398/400); SIGNAL-2026-08-30-1116 (`test_gate_logic.py` 598/600);
SIGNAL-2026-07-28-0134 (делегаты `db.py` вывели бы файл на 395-407/400);
плюс замер сегодня.
**Type:** design_decision

`wc -l`, 2026-08-30:

| Файл | LOC | Лимит | Headroom |
|---|---|---|---|
| `scripts/vps/orchestrator_queue.py` | **400** | 400 | **0** |
| `scripts/vps/callback.py` | **400** | 400 | **0** |
| `scripts/vps/gate-daemon.py` | 398 | 400 | 2 |
| `scripts/vps/tests/test_gate_logic.py` | 598 | 600 | 2 |

Четыре файла — и это ровно те четыре, вокруг которых крутится критический путь оркестратора.
Совпадение исключено: ноль headroom — не случайность, а **равновесие**, к которому притягивает
правило «max 400 LOC» без ратчета. Расколол → освободил место → следующая спека заполнила его
до потолка → следующая упирается. В прошлой сессии этот пункт был отправлен «ниже порога»
(одно попадание `gate-daemon.py`); за один день их стало четыре, и `callback.py` — новый.

Практическая цена уже наблюдалась дважды: SIGNAL-1116 (кодеру пришлось заводить файл вне
allowlist, потому что дописывать в 598/600 было некуда) и SIGNAL-0134 (спека, выполненная
буквально, не достигла бы собственной цели). То есть это не эстетика — это класс срыва спек,
который K1 уже пытается ловить со стороны allowlist.

**Внешнее подтверждение.** Голый порог — известный анти-паттерн; рабочая форма — **ратчет с
grandfathering**:
- `file-size-ratchet` (noctcore/eslint-plugins): cap 400 сырых строк (`wc -l`-семантика,
  «число, которое автор видит в редакторе = число, которое видит гейт»), сегодняшние нарушители
  заморожены в закоммиченном baseline; **новый нарушитель или выросший замороженный — fail**;
  baseline **самозатягивается**, если файл ужался. <https://github.com/noctcore/eslint-plugins/blob/main/packages/lint-meta-rules/src/rules/file-size-ratchet.ts>
- «Every God File Split: Enforcing a 400-Line Cap Across a Video Pipeline» (dev.to, 2026-08-25) —
  тот же cap 400 и **буквально наш симптом**: «a shared job-types file that had hit its own size
  cap at **exactly zero lines of headroom**», из-за чего семь типов пришлось выносить заранее,
  «чтобы следующему было куда пойти без поднятия cap». Механизм у них: boundaries-тест диффает
  рабочее дерево против main и валит билд на любом net-changed файле из ledger — «you touch it,
  you split it». <https://dev.to/humzakt/every-god-file-split-enforcing-a-400-line-cap-across-a-video-pipeline-6jd>
- Ratchet pattern в общем виде (Rational Partners, 2026-05-25): метрика в закоммиченном
  baseline, регресс = fail, улучшение = автоматическое затягивание пола.
  <https://rational.partners/insights/the-ratchet-pattern>

**Proposed action:** превратить «max 400 LOC» из порога в ратчет — закоммиченный baseline
`LOC` по файлу, гейт валит **рост** файла, стоящего на потолке, а не только пересечение 400.
Плюс `.claude/skills/spark` Phase 5.5: если файл в `## Allowed Files` имеет headroom < 50 строк,
а reason содержит «дописать/расширить/add tests» — error, спека обязана содержать раскол
(это буквально K1(а) из прошлой сессии, здесь она получает вторую, независимую мотивацию).

## L4 (carry-forward, эскалация): §Design отгружает дословные команды, которые никто не выполнил

прежнее — SIGNAL-2026-08-30-1115, SIGNAL-2026-08-30-arch-219 §Process signal,
SIGNAL-2026-07-28-1210.
**Type:** failure_pattern

TECH-221 §Design содержал bash-сниппет `git worktree add <path> <branch>` **без `-b`** — это
detached HEAD (`worktree.guessRemote` по умолчанию выключен). Поймал планнер (Drift D3), и
только потому, что перечитывал код. Ровно тот же класс, что merge-base-диапазон в TECH-220 и
`get_db()`-сниппет в TECH-212: спека пишет исполняемый код в §Design и не исполняет его ни разу.

Порог 3 был пройден в прошлой сессии; здесь фиксируется, что **лечение не применено и рецидив
случился в следующей же спеке**. Предложение сужается до одного механического правила, которое
уже можно проверить кодом:

**Proposed action:** любой fenced `bash`/`sh`-блок в §Design спеки — исполняемый артефакт.
Перед `queued` он либо (а) прогоняется один раз на одноразовом репо (TECH-221 Task 4 так и
делал — и именно так был найден data-loss), либо (б) заменяется ссылкой `file:line` на место,
где эта команда уже живёт и работает. Линтер спеки: fenced `bash` в §Design без соседней
`file:line`-ссылки и без пометки «verified on throwaway repo» → warning.

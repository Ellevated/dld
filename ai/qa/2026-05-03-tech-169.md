## Failures

### F1: Reset-CLI шлёт ложный Telegram-алёрт когда circuit НЕ был открыт

**Severity:** Minor
**Reproducibility:** Always
**Expected:** Если circuit closed — `--reset-circuit` тихо чистит decisions, без алёрта. Reset-event имеет смысл только после реального OPEN.
**Actual:** CLI всегда вызывает `event_writer.notify_circuit_event(action='reset')` → в OpenClaw/Telegram приходит "CIRCUIT_RESET: operator reset — decisions cleared, claude-runner resumed", даже если состояние было нормальное.
**Steps to reproduce:**
1. Прод-БД, circuit closed, 0-2 demotes в окне.
2. Оператор любопытствует: `python3 callback.py --reset-circuit`
3. В Telegram прилетает CIRCUIT_RESET — оператор пугается, думает что был инцидент.

**Evidence:** При QA-прогоне случайно зацепил прод-БД (см. F2) и в `scripts/vps/ai/openclaw/pending-events/` появился `20260503-013646-circuit_breaker.json` без предшествующего OPEN.
**User impact:** Алёрт-усталость. Тревожный статус в чате без инцидента подрывает доверие к каналу.
**Hint for developers:** `_reset_circuit_cli` сначала проверить `is_circuit_open()` или хотя бы `count_demotes_since(WINDOW)` > 0, и только тогда `notify_circuit_event`. Либо два action: `reset_after_open` vs `manual_clear`.

### F2: Env-var для override БД называется `DB_PATH` без `DLD_`-префикса

**Severity:** Minor (DX/safety)
**Reproducibility:** Always
**Expected:** В DLD-конвенции env-переменные имеют префикс `DLD_*` (см. `DLD_*` упоминания в orchestrator). При QA/тестировании естественно пробовать `DLD_DB_PATH` для изоляции.
**Actual:** Реальное имя — `DB_PATH` (`scripts/vps/db.py:18`). Запуск `DLD_DB_PATH=/tmp/test.db python3 callback.py --reset-circuit` молча игнорирует override и бьёт по проду.
**Steps to reproduce:**
1. `DLD_DB_PATH=/tmp/x.db python3 scripts/vps/callback.py --reset-circuit`
2. Команда работает с `scripts/vps/orchestrator.db` (прод), не с `/tmp/x.db`.

**Evidence:** Во время QA первый прогон CLI с `DLD_DB_PATH` очистил 8 строк из прод-таблицы `callback_decisions` и вызвал `pueue start --group claude-runner` на живом демоне (no-op, но факт).
**User impact:** Любая попытка safe-test'а на проде превращается в реальную операцию. Особенно опасно для `--reset-circuit` (destructive).
**Hint for developers:** Переименовать в `DLD_DB_PATH` или добавить алиас. Альтернатива — добавить `--db PATH` CLI-флаг для callback.py, не полагаться на env.

## Observations (не баги, на заметку)

### O1: Auto-heal HEAL_MIN-ветка логически dead code

`is_circuit_open` (`callback.py:924`):
```python
if recent > CIRCUIT_THRESHOLD:           # 10-мин окно
    heal = db.count_demotes_since(30)    # 30-мин окно ⊇ 10-мин
    if heal == 0: return False           # недостижимо: heal >= recent > 3
```
30-мин окно ВКЛЮЧАЕТ 10-мин, поэтому `heal >= recent`, и `heal == 0` невозможно когда `recent > 3`. Ветка никогда не срабатывает. Безопасно: фактический auto-heal происходит естественно через истечение 10-мин окна (`recent` падает до 0). Спецификация EC-3 выполняется, но не той логикой, что предполагалось.

**Hint:** Либо удалить мёртвую ветку, либо реальный auto-heal должен сравнивать "ts последнего demote" с now-HEAL_MIN, а не считать в окне.

### O2: Каждый verify_status_sync пишет 2 строки на demote

В прод-таблице видно пары: одна `verdict='demote' demoted=1`, сразу за ней `verdict='noop' demoted=0` с тем же ts/spec. `demoted=0` правильно не учитывается в threshold, но удваивает объём аудит-таблицы. Не критично, INDEX по ts держит запросы быстрыми.

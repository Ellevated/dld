## Что было

`codebase-memory` (внешний OSS MCP) прописан на VPS в `~/.claude.json` на уровне
пользователя, индексы всех проектов лежат в `~/.cache/codebase-memory-mcp/`. То есть
сервер поднимается в каждом прогоне и кладёт определения своих инструментов в контекст —
а звать его некому: у `planner.md`, `coder.md`, `tester.md` его не было в `tools`, и
промпты автопилота его не упоминали. Единственный агент с доступом — `spark-codebase`.

Цифра «15.9× экономии против grep» из разбора 28.08 измерена в интерактивной сессии на
одном `trace_path` — там, где граф и был подключён (Impact Tree в CLAUDE.md, `/spark`).
Автопилот, где уходят деньги, не видел его ни разу. Ощущение founder'а «я этого места
вообще не почувствовал» — верное, и это не про деградацию.

## Что изменено

1. `planner.md` (оба дерева) — `list_projects`, `trace_path`, `search_code`, `search_graph`
   в `tools` + секция «Impact Tree: ask the code graph before grepping the tree»: UP/DOWN
   через `trace_path`, найденные вызывающие стороны перечисляются в задаче, меняющей
   сигнатуру.
2. `coder.md` (оба дерева) — `list_projects`, `trace_path`, `search_code` в `tools` + две
   строки в «Research Tools»: перед изменением сигнатуры — `trace_path` inbound, обновить
   всех вызывающих в этой же задаче.
3. В обоих промптах названы границы: индекс — снимок дефолтной ветки (на 05.09 индексы
   были от 28.08, восемь дней несвежести), поэтому приёмка на переименование остаётся
   `grep` по рабочему дереву = 0; граф недоступен → продолжать грепом, не чинить индекс,
   не тратить ход.

## Механизм, который проверяем

Инструмент, которого нет в `tools`, не может быть вызван; инструмент, который есть, но о
котором не сказано, когда его звать, — не вызывается. Проверяем вторую половину: хватит
ли явной инструкции.

## Если не сработает

Ноль вызовов и с доступом = держать сервер на VPS незачем. Снимаем из `~/.claude.json`
на VPS (интерактивные сессии на ноутбуке не трогаем — там он окупается через `/spark` и
Impact Tree) и экономим определения инструментов в контексте каждого из ~12 агентов на
прогон. «Подключён, но не зовётся» — худший из трёх вариантов, и это состояние держалось
четыре месяца.

## Поправка 06.09 — сервер не поднимался, мерить было нечего

Через сутки после открытия эксперимента выяснилось, что он мерил не поведение агентов, а
доступность сервера. Замер холодного старта: `codebase-memory-mcp` отвечает на `initialize`
за **30.58 с** (бинарь 293 МБ), а CLI даёт MCP-серверу ровно **30 000 мс** и отключает его.
Промах на полсекунды, стабильно.

По транскриптам всех проектов:

| Период | Сессий | CONNECT_TIMEOUT | Вызовов графа |
|---|---|---|---|
| 01.08–15.08 | 708 | 0 | 0 |
| 15.08–01.09 | 615 | 0 | 0 |
| 01.09–05.09 | 448 | 97 | 0 |
| 05.09–06.09 (после раскатки tools) | 48 | **21** | 0 |

То есть строка baseline «сервер при этом стартовал в каждом прогоне» верна до 01.09 и
неверна после: в 44% сентябрьских сессий графа в контексте не было вообще. Вердикт «ноль
вызовов ⇒ снимаем сервер» на таких данных был бы сделан о сервере, который не запускался.

Исправлено: `MCP_TIMEOUT=90000` в `scripts/vps/.env` (+ `.env.example`) для прогонов флота
и в `~/.claude/settings.json` для интерактивных сессий на этой машине. Проверка:
`MCP_TIMEOUT=90000 claude mcp list` → `codebase-memory ✔ Connected`. Задержка не выросла —
эти 30 с и так тратились, просто выбрасывались в конце.

Окно замера перезапущено с 06.09; прогоны, где в транскрипте есть
`codebase-memory connection timed out`, из знаменателя исключаются — они ничего не говорят
о том, зовут ли агенты граф.

Отдельный вопрос, который этот эксперимент НЕ проверяет: свежесть индексов. Полный ребилд
awardybot — секунды (14 с на 130k узлов, замер 28.08), но никто его не запускает по
расписанию. Если вызовы появятся, следующий шаг — крон на переиндексацию, иначе граф будет
отвечать про позавчерашний код.

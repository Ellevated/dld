# Автопилот на оркестраторе: почему 2–3 часа и $15–50 за спеку

Разбор по данным VPS (`task_log`, per-run JSON-логи, транскрипты сессий Claude Code за
07.08–02.09) и по истории промптов в этом репо. Вопрос: почему спека, которую в интерактиве
делают за 10–30 минут, на оркестраторе живёт 2–3 часа и упирается даже в поднятый до 3 часов
таймаут, и что изменилось с мая–июня.

## Вывод в трёх строках

1. **Половина времени прогона — не модель, а `pytest`.** Один прогон `tests/architecture/`
   awardybot — 5–9 минут на любой машине (VPS пустой 333 с, твой ноутбук 517 с), а конвейер
   запускает тяжёлые наборы 5–6 раз на спеку: baseline в PHASE 0, тестер по 2–3 раза на каждой
   задаче, кодер сам, гейты main loop, `./test ci` дважды в PHASE 3. `steal` 30–70 % на VPS
   в рабочие часы добавляет сверху проценты, не разы.
2. **Вторая половина — конвейер из 12–14 холодных агентов на спеку**, каждый стартует с
   28–46K токенов системного промпта и разгоняется до 160–390K, плюс main loop на Opus, который
   с 25–27.07 делает review, spec-compliance и гейты сам: 220 сообщений и 108 Bash-вызовов на
   одну спеку. Деньги уходят в cache read: 27M токенов на Opus и 42M на Sonnet за один прогон.
3. **Май «быстрым» был наполовину фиктивно.** Медиана 2 минуты — это петли re-dispatch и
   ранние выходы «уже сделано / blocked». Реальные майские прогоны (≥25 ходов) стоили $7.4 и
   шли 20–50 минут. Сейчас медиана $15–17 и 124 минуты, то есть честное замедление ×3 и
   удорожание ×2, а не ×10.

## VPS и `steal`: множитель, но не главный

`sar` за 28.08 и 02.09, почасовые средние:

| Час (28.08) | steal | idle | Час (02.09) | steal | idle |
|-------------|------:|-----:|-------------|------:|-----:|
| 01:00 | 65 % | 11 % | 09:00 | 70 % | 6 % |
| 11:00 | 56 % | 22 % | 13:00 | 69 % | 6 % |
| 13:00 | 69 % | 6 % | 14:00 | 62 % | 14 % |
| 15:00 | 70 % | 5 % | 16:00 | 46 % | 35 % |
| 23:00 | 66 % | 8 % | ночь | 6 % | 88 % |

Среднесуточный `steal` 27–30.08 — 30–42 %. Это не наша нагрузка, это сосед по гипервизору:
как только мы грузим CPU, хостер забирает от трети до двух третей тактов. На 6 vCPU при этом
идут 2–3 параллельных прогона, каждый с `pytest -n 4` (addopts в `pyproject.toml` awardybot),
то есть 8–12 воркеров на 2–4 реально доступных ядра.

Сравнение одного и того же набора `tests/architecture/` (awardybot, `-p no:cacheprovider`):

| Где | Секунд |
|-----|-------:|
| VPS под нагрузкой (внутри тестера FTR-1487) | 282 и 432 |
| VPS ночью, пустой (load 0.99, steal 0 %) | 333 (1813 passed) |
| Машина Олега (Windows, тот же коммит) | 517 (1722 passed, 94 failed — Windows-специфика) |

Замер 02.09 23:14 местного. Вывод неожиданный и важный: **набор сам по себе занимает 5–9 минут
на любой машине**, а под нагрузкой на VPS — 4.7–7.2. `steal` добавляет проценты, не разы.
Значит, главный множитель — не хостер, а **сколько раз конвейер запускает этот набор**: в
FTR-1487 тестер гонял `tests/architecture/` дважды на задаче, плюс baseline `./test fast`
(куда он входит) в PHASE 0, плюс `./test ci` дважды в PHASE 3. Пять–шесть прогонов по
5–7 минут — вот откуда 40–90 минут pytest на спеку.

## Почему интерактив быстрее — по пунктам

| Автопилот на VPS | Интерактив на ноутбуке |
|------------------|------------------------|
| PHASE 0: `./test fast` целиком до начала работы (5–30 мин) | не делается |
| PHASE 1: planner на Opus всегда, даже если план в спеке есть (10–16 мин) | план держится в голове сессии |
| На каждую задачу холодный coder + холодный tester: старт 28–35K токенов, обязательное чтение `architecture.md` + `dependencies.md` + `domains/*.md` (в awardybot это 6.2K + 3.4K + 19.7K слов), в конце `context-updater` пишет обратно в domain-файлы | один контекст, читается только то, что нужно |
| Тестер гоняет позиционные наборы + `tests/architecture/` по 2–3 раза на задачу | целевой тест один раз, полный набор — один раз в конце |
| Main loop после каждой задачи: spec compliance, review по чеклисту `review.md`, ratchet, size gates, arch gates — 10 Bash-вызовов по 1 минуте (все на VPS с steal) | коммит |
| PHASE 3: `./test ci` на ветке, потом ещё раз на смерженном дереве, Exa-верификация, reflect, documenter | push |
| После done: отдельный `/qa` (17 мин) и `/reflect` (14 мин) | нет |
| 2–3 прогона делят 6 vCPU с 30–70 % steal | вся машина твоя |

Дело не в окне контекста и не в «модель думает дольше»: thinking-токены в прогоне —
единицы процентов расхода, а задержка модели в main loop — медиана 4 секунды на сообщение.
Дело в **количестве сообщений и запусков pytest**, которое сам конвейер и назначает.

## Что с этим делать (рычаги по убыванию эффекта)

1. **Тесты: один целевой прогон на задачу, один полный — на спеку.** Убрать baseline
   `./test fast` из PHASE 0 (CI на `origin/develop` уже проверяется `ci-status.sh`), запретить
   тестеру `tests/architecture/` и полные наборы на задаче — они идут один раз в PHASE 3.
   Ожидаемый эффект: −40…−70 минут на спеку, −30 % стоимости Sonnet.
2. **Main loop не гоняет гейты после каждой задачи.** Ratchet, size gates, arch gates — один раз
   перед коммитом задачи, не по 10 вызовов. Либо вернуть review в один субагент на Sonnet, но
   с явным запретом на запуск pytest. Эффект: −15…−50 минут, −25 % стоимости Opus.
3. **Planner условный.** Если спека моложе N дней и `Drift Log` пуст — планировщик проверяет
   пути `Glob`-ом и выходит, а не перечитывает 350K токенов кода на Opus high. Эффект: −10 минут
   и −$3…5 на каждой спеке.
4. **Холодный старт субагентов дешевле.** `context-loader` заставляет каждый coder читать
   `architecture.md` + `dependencies.md` + все затронутые `domains/*.md` (в awardybot ~30K слов),
   `context-updater` — писать обратно. Сделать чтение по требованию (grep по имени сущности),
   а обновление контекста — одной задачей в PHASE 3. Эффект: −20…−30 % cache write у Sonnet.
5. **Сам набор `tests/architecture/` — 1813 тестов за 5,5 минут на пустой машине.** Это
   архитектурные проверки (AST, импорты, golden-файлы), которым не нужно 5 минут; профилировать
   `--durations=20` и вынести тяжёлые в отдельный маркер, который гоняется раз в PHASE 3. Хостер
   и `steal` — второстепенно: под нагрузкой 4.7–7.2 мин против 5.5 на пустой.
6. **`/qa` и `/reflect` — не после каждой спеки.** 31 минута и ~$8 на спеку. `/reflect` — раз в
   сутки по проекту, `/qa` — только для FTR/BUG с `## Acceptance Verification`.

Первые два пункта — правки промптов в `.claude/skills/autopilot/` и `.claude/agents/tester.md`
в обоих деревьях, без кода оркестратора. Мерить после — тем же скриптом, что писал этот разбор:
`/tmp/ap/batch.py <дата>` на VPS раскладывает каждый прогон по категориям из транскриптов.

## Что сделано 03.09 — рычаги 1 и 2

Правки промптов, оба дерева (`.claude/` и `template/.claude/`), код оркестратора не тронут.
Гейты зелёные: `check-prompt-integrity` ×2, `check-tree-sync`, `check-rules-loading`,
пять harness-сьютов `test/scripts`, `pytest tests/unit` (196).

**Рычаг 1 — тесты один раз на задачу, полный набор один раз на спеку:**
- `worktree-setup.md` шаг 9 и `autopilot-git.md` §2.6: baseline `./test fast` в PHASE 0 убран,
  базой считается CI на `origin/develop`, который шаг 1 уже проверяет.
- `tester.md`: новая секция «Test Budget» — одна выборка, один прогон, после фикса перегон только
  упавших id, запрет на `./test fast|ci`, `tests/architecture/`, целые `tests/`/`src/`,
  бюджет 10 минут pytest на диспатч; fallback «нет совпадения → полный набор» заменён на
  «свой тест-файл, иначе `no_tests_selected`».
- `coder.md` шаг 6: кодер гоняет только тесты своей задачи, один раз, после фикса — упавшие id.
- `task-loop.md` Step 2: тестеру передаётся `pytest {Test: файлы задачи}`, а не `./test fast`.
- `finishing.md` + `autopilot-git.md` §5.1/§5.4: `./test ci` — единственный полный прогон; шаг 8
  сравнивает `git rev-parse HEAD^{tree}` с деревом, проверенным на шаге 1, и при совпадении
  логирует `CI_PARITY_REUSED` вместо второго 5–25-минутного прогона.

**Рычаг 2 — main loop не гоняет гейты после каждой задачи:**
- `task-loop.md`: секция «What the loop never runs» — main loop не запускает pytest, `./test *`,

  названные скрипты, один прогон на задачу, после возврата от кодера перегоняется только
